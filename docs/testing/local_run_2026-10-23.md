# Local run, 23 Oct 2026 — real LLM + real checker models (for Aditya / M2)

**Setup.** Mac M4 16 GB, branch `m1/integration` (4ee8dcf). Agent: `qwen3:8b` via Ollama with thinking disabled
(`think: false`; with thinking on, each call took ~14 s instead of 0.5 s). Checkers: MiniCheck-RoBERTa-Large,
`cross-encoder/nli-deberta-v3-base`, `protectai/deberta-v3-base-prompt-injection-v2` (Prompt Guard 2 is gated) on MPS.
Episodes: M3 scenario generator `--seed 1`, dev split, 36 episodes (recall 12, cross_team 12, clearance 6,
shared_recall 2, payment 2, fake_fact 2). Driver: `docs/testing/local_bench.py` (M3 `run_episode` + M1 `build_service`).

Good: full blocks every leak (all leaks elsewhere are cross_team / clearance attacks) and both fake-fact payment

Problem: with the real models, **full holds all 4 legitimate payments for human approval** (false denial 100%).
Two causes, both in M2's area:

## Issue 1 — contradiction check flags facts about different subjects (guards/contradiction.py)

DeBERTa-NLI returns P(contradiction) = 1.00 for template-similar facts about *different* entities:

| premise | hypothesis | P(contradiction) | correct? |
|---|---|---|---|
| Project Vorliooru measured a BLEU of 81.402 on Saltmarsh | Project Kestrane measured a BLEU of 75.210 on Saltmarsh | 1.00 | no (different projects) |
| Project Vorliooru … 81.402 | Project Vorliooru … 64.000 | 1.00 | yes |
| Acme Ltd's bank account is 56564275 | … has changed to 58974948 | 1.00 | yes (or update) |

So ordinary seed memories become *contested*, which then feeds Issue 2.

**Suggested fix:** only run NLI on pairs that share a subject. Extract a subject key per claim (named entity /
project codename / vendor; or the (subject, property) of the triple from Check 3) and compare only claims with the
same key (fall back to high embedding similarity **and** shared proper nouns). Optionally require
P(contradiction) ≥ 0.9 and P(contradiction) − P(entailment) margin. Add the table above as unit tests.

## Issue 2 — action gate checks every claim in context, not the parameter claims (policy/gate.py)

The legitimate payment had its account correctly bound from the registry
(`{"vendor": "Ember Optics", "account": "24015581"}`) but was queued because 6 retrieved context claims were
"untrusted, contested or quarantined". The deck's rule (slide 9, action gate) is: a high-risk call is allowed iff
every claim **its parameters depend on** is Protected (registry) or Verified. Registry-bound parameters satisfy that.

**Suggested fix:** compute Ctx(a) as the claims that supplied parameter values (none, when every risky parameter is
registry-bound), not the whole retrieved context; keep the taint rule (session read untrusted input → no high-risk
call with *model-supplied* parameters). Add a test: contested-but-irrelevant memories in context + registry-bound
payment → allowed; attacker account from memory → blocked.
